## 1. 프로젝트를 한 문장으로

“장애 질문을 받으면 시스템 상태와 대응 매뉴얼을 조회하고, 출처와 조치 조건을 검사해 보고서를 제공하는 에이전트입니다.”

실제 서버를 재시작하는 프로그램이 아니라 **조사와 대응 판단을 돕는 프로그램**이다. 모니터링은 교육용 샘플이며 현재 수치에 변동이 생긴다.

## 2. 제공된 기능과 내가 개선한 부분

| 구분 | 설명 |
|---|---|
| 제공된 기반 | FastAPI, Vue 채팅·SSE, MCP 연결, 기본 Agent Graph, 모델 교체, SQLite 대화 저장, LangSmith 추적 |
| 개선 | 조사 대상 확인, 질문 분류·복수 시스템 계획 보완, 시스템별 수집·부분 실패 처리 |
| 추가 | 임베딩 기반 런북 검색과 증상별 검색·제외 조건·매뉴얼 없음 처리 |
| 추가·개선 | 출처·시스템·조치 조건·요청 범위 검증, 재작성과 사실 보고서 |
| 개선 | Graph 노드 모듈 분리, 보고서 요약·접힌 근거·진행 시간·오류 안내 |
| 추가 | 자동 테스트와 개선 전후 평가 자료 |

MCP나 LangSmith 자체를 처음부터 만들었다고 설명하지 않는다. 기존 Graph 파일을 나눈 것은 **노드 모듈화**이며, 전문 에이전트 3개로 된 새로운 Research 서브그래프를 구현한 것은 아니다.

## 3. 흐름은 질문 하나로 외우기

예시: **“payments-service의 CPU와 메모리 사용량이 높아요. 각각 대응 방법을 알려주세요.”**

```text
web_chat.html: 사용자가 질문 입력
    ↓
server.py: 요청 접수, 모델·MCP·검색기가 연결된 Graph 실행
    ↓
target_check: payments-service가 등록된 시스템인지 확인
    ↓
route: 일반 대화인지 장애 조사인지 구분
    ↓
plan → gate: 조사 계획을 만들고 불필요한 작업 제외
    ↓
research: MCP Tool로 모니터링 조회
    ↓
replan_check: CPU와 메모리를 각각 의미 검색
    ↓
research: 선택된 런북 원문을 MCP Resource로 조회
    ↓
analysis → write: 분석, 근거에 맞는 구조화된 초안 생성
    ↓
validate: 출처·대상·단계·조건·요청 범위 검사
    ├─ 실패: 피드백 후 재작성, 최대 3회
    └─ 통과 또는 반복 한도: finalize
    ↓
reporting.py: 최종 보고서 구성
    ↓
web_chat.html: 요약 표시, 상세 근거는 접어서 제공
```

자료 조회 실패나 적합한 매뉴얼이 없는 경우에는 확보한 사실을 유지하고 **원인·조치 제안 생성과 검증을 생략**한다. 반복 검증 실패는 강제 통과가 아니다.

## 4. state와 deps는 이렇게 이해하기

**state = 이번 질문의 작업 기록장** → [agent/state.py:4](../../../agent/state.py#L4)

```python
query                # 사용자 질문
registered_targets   # 조사할 시스템
tasks                # 해야 할 일
collected            # 수집한 모니터링·런북
collection_failures  # 실패한 조회 기록
validation_passed    # 검사 통과 여부
```

위는 항목 설명이며 실행 코드는 아니다. 각 노드는 이 기록장을 읽고 결과를 반환한다. LangGraph가 반환된 값을 반영해서 다음 노드에 전달한다.

**deps = 함께 쓰는 도구 상자** → [agent/deps.py:12](../../../agent/deps.py#L12)

```python
fast_llm        # 분류·계획 등에 쓰는 모델
quality_llm     # 초안 작성 모델
mcp             # 외부 조회 연결
runbook_search  # 런북 검색기
```

“질문마다 바뀌는 정보는 state에, 모델·검색기처럼 공통으로 사용하는 도구는 deps에 담았습니다.”라고 설명하면 된다. 검색기를 기존 의존성 주입 구조에 추가한 것이다.

## 5. 발표에서 열어볼 핵심 코드

data, retries = await with_retry(

### C. RAG — 관련 매뉴얼 선택

연결 위치: [agent/nodes/research.py:118](../../../agent/nodes/research.py#L118)

```python
details = await retriever.search_request(
    state["query"], name,
    state["registered_targets"], monitoring[0]["data"])
hits = details["hits"]
```

발표 문장: **“시스템별로 질문과 수집 자료를 검색기에 넘기고, 선택된 문서를 조회 작업에 추가합니다.”**

검색 정책: [agent/runbook_search.py:93](../../../agent/runbook_search.py#L93) / [agent/runbook_search.py:187](../../../agent/runbook_search.py#L187)

```python
for kind in scope["included"]:
    candidates = await self.search(TOPICS[kind][1])
    matches = [h for h in candidates
               if h["incident_type"] == kind]
```

발표 문장: **“CPU와 메모리를 한 번에 검색하면 한 증상이 밀릴 수 있어 각각 의미 검색하고 합칩니다. 제외한 증상은 대응에서 빼고, 검색에 실패하거나 점수가 부족하면 임의 문서로 대체하지 않습니다.”**

중요한 구분: 증상·제외 범위 추출은 현재 6개 런북에 맞춘 **표현 규칙**, 문서 검색은 **임베딩 유사도**다. 키워드로 무조건 런북을 집어넣는 폴백은 아니다.

실제 유사도 계산: [agent/runbook_search.py:167](../../../agent/runbook_search.py#L167)

```python
score = sum(a * b for a, b in zip(vector, stored))
```

문서와 질문을 숫자 벡터로 바꾸고 정규화한 뒤 의미 유사도를 비교한다. 최소 점수 0.43, 최고 점수와 차이 0.08 이내, 개별 검색 최대 2개 조건을 적용한다. 증상별 합집합은 2개를 넘을 수 있다. 점수는 정답 확률이 아니다.

**왜 RAG인가?** 문서를 검색하는 것으로 끝나지 않고, 선택한 원문을 AI 작성 입력에 넣어 답변 근거로 활용하기 때문이다. 기존 매뉴얼 6개 원문은 변경하지 않았다.

### D. 검증·보고서 — AI 초안을 그대로 내보내지 않기

위치: [agent/nodes/writing.py:28](../../../agent/nodes/writing.py#L28) / [agent/evidence.py:80](../../../agent/evidence.py#L80)

```python
proposal, issues = validate_proposal(
    state["draft"], state.get("collected", []),
    state.get("registered_targets", []))
```

발표 문장: **“AI에게 출처와 조치 번호가 포함된 JSON 초안을 받고 코드가 검사합니다. 현재 메모리가 56%라면 90% 이상을 전제로 한 재시작 조치는 보류합니다. 검증 실패 시 피드백으로 재작성하며, 반복 실패해도 통과시키지 않습니다.”**

이후 요청 증상 누락·제외 대응·범위 밖 런북도 검사한다. 모든 의학적·운영적 인과관계나 자연어 정확성을 검증하는 것은 아니며, LLM-as-a-Judge 구현도 아니다.

출력 구성: [agent/reporting.py:9](../../../agent/reporting.py#L9) / [web_chat.html:105](../../../web_chat.html#L105)

“검증한 자료로 보고서를 구성하고, 화면에서는 상태·원인 판단·우선 확인 사항을 먼저 표시했습니다. 전체 출처와 조건은 접어서 열 수 있습니다.”

실시간 전달·오류 처리: [server.py:167](../../../server.py#L167)

“진행 이벤트를 SSE로 전달하고, 화면은 경과 시간과 지연을 표시합니다. 서버 오류와 연결 끊김도 안내합니다.”

## 7. 준비할 캡처와 주의사항

1. CPU·메모리 질문: 검색 결과 `cpu-spike`, `memory-leak`가 함께 보이도록 상세를 열어 캡처.
2. 같은 질문의 요약 보고서: 현재 수치, 조건 미충족 조치 보류가 보이도록 캡처.
3. TLS 질문: 확인 불가·제외 조건·매뉴얼 없음 안내 캡처.
4. 미등록·미지정 시스템 질문: 대상 확인 질문 캡처.
5. 전후 비교를 넣는다면 같은 질문의 전후 캡처를 함께 제시. 전체 정확도 향상률로 확대 해석하지 않기.

최신 실행 캡처 5장과 화면 텍스트를 프로젝트 `docs/presentation/captures/`에 저장했다. CPU·메모리, TLS, 미등록·미지정 대상의 실제 8600 화면이며 전체 10개 회귀 사례 캡처를 뜻하지 않는다.

## 8. 검증 범위와 남은 한계

- 자동 테스트 76개는 로직·실패 처리 검증이며, 모든 자연어 검색의 정답률이 아니다.
- 최신 대표 실행: 실제 MCP·Qwen3 0.6B/8B에서 CPU·메모리 복합 질문 10.83초, TLS 질문 1.79초. 서로 다른 질문의 시간이므로 속도 개선율로 비교하지 않는다.
- 증거: `docs/evaluation/rag_scope_pipeline_20261021.json`, `rag_scope_retrieval_20261021.json`.
- 기존 LangSmith 추적을 활용하지만 이 기록만으로 최종 답변이 정확하다고 판단하지 않는다.
- 복잡한 포함·제외 표현, 복수 시스템의 공통 증상, 새로운 표현은 추가 평가가 필요하다.
- 대상 확인 후 원래 질문을 복원하는 대화 연결, 동기 모델 호출, 분석 노드 결과의 활용은 후속 개선 과제다.
- 위험 조치를 실행하는 기능과 Human-in-the-loop 승인 노드는 구현하지 않았다.

## 9. 이번 발표 전 마무리 수정

- 메모리 런북을 참고한 보고서에만 메모리 누수 안내를 표시해 TLS 질문의 불필요한 설명을 제거했다.
- 제외한 대응 이름을 `cpu-spike` 같은 내부 ID 대신 CPU 급증·메모리 문제·응답 지연 등 한국어로 표시했다.
- 생성하는 곳이 없는 이전 진행 이벤트 표시 항목을 제거했다.

화면 변경은 브라우저 새로고침으로 반영된다. 앞선 Python 변경을 아직 적용하지 않았다면 백엔드도 한 번 재시작한다. Ollama 자체 재시작은 필요 없다.
