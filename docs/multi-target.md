# 개선 2: 복수 시스템 조사와 매뉴얼 누락 방지

## 문제

기준 사례 08은 payments-service와 cache-service를 요청했지만 payments만 조사했다. 계획의 일부 누락을 기존 코드는 복구하지 않았고, 매뉴얼 하나만 있으면 전체 자료가 충분하다고 판단했다. 합쳐진 알림에서 첫 키워드를 고르므로 서로 다른 장애의 매뉴얼도 구분하지 못했다.

## 변경

1. `agent/planning.py`: 모델 계획과 명시된 등록 시스템을 대조한다. 누락 대상 보완, 중복 제거, 요청하지 않은 대상 제외. 조회는 시스템별 한 번씩 수행한다. analysis 작업은 기존 gate 판단에 맡긴다.
2. `replan_check_node`: 각 시스템의 알림을 따로 분류해 시스템별 runbook 작업을 생성한다. 한 번의 재조사에서 모든 누락 매뉴얼을 수집한다. 모니터링/매뉴얼이 끝까지 빠졌다면 충분하다고 위장하지 않고 오류를 반환한다.
3. 수집 데이터와 TaskCompleted 이벤트에 system_name을 기록한다. 작성 모델에 시스템별 매뉴얼을 명확히 표시하고 전체 대상 반영을 지시한다. fake 작성기도 모든 매뉴얼을 사용한다.
4. 검증 시 복수 대상 이름 누락을 확인하고 재작성한다. 3회 한도 이후에도 대상이 빠지면 해당 시스템의 실제 수집 상태와 매뉴얼을 최종 응답에 표시해 근거를 보충한다. 최종 응답은 Vue의 FinalAnswer에서 반영된다.
5. Vue에 누락 대상 보완 단계와 시스템별 매뉴얼 조회를 표시한다.

## 검증

```bash
PYTHONDONTWRITEBYTECODE=1 LANGCHAIN_TRACING_V2=false LANGSMITH_TRACING=false .venv/bin/python3 -m unittest discover -s tests -v
```

24개 자동 테스트 통과(기존 13 + 신규 11). 모델 계획에 payments만 넣는 mock으로 누락을 재현해 두 시스템을 모두 호출하는지 확인했다. 서로 다른/동일 장애, 빈 계획, 중복, 요청하지 않은 대상, 기존 단일 시스템, 일부 매뉴얼만 존재하는 상태, 누락 데이터 오류, 스트리밍 이벤트, 반복적인 답변 누락 보충을 검사한다.

이 테스트는 고정 mock/fake 데이터 검증이며 실제 Ollama 성능·지연시간 또는 정확도 개선 수치가 아니다. 개선 전 캡처는 그대로 보존한다.

## 실제 화면 확인

서버 재시작과 Vue 새로고침 후 기준 08 질문을 동일하게 입력한다.

> payments-service와 cache-service 상태를 각각 확인하고 필요한 대응 매뉴얼을 알려주세요.

기대: 모니터링 payments/cache 모두 표시, payments에는 cpu-spike, cache에는 memory-leak 매뉴얼 표시. 최종 프롬프트에 두 시스템의 모니터링과 연결된 매뉴얼이 존재해야 한다. 실제 모델이 incident로 분류해야 이 조사 경로에 진입하며, 질문 오분류는 다음 단계의 개선 대상이다.

## 한계와 트레이드오프

- 명시된 시스템만 조사해 모델의 임의 추가 대상은 제외한다. 암묵적 연관 시스템 탐색은 지원하지 않는다.
- 단일 시스템의 복합 장애는 기존 키워드 우선순위와 db-down 기본값을 유지한다. 의미 검색은 별도 과제다.
- 같은 장애의 두 시스템도 매뉴얼은 각각 조회한다. 호출 증가와 긴 답변이 발생할 수 있다.
- 이름 포함 검증은 형식적 범위 검사다. 해당 시스템의 설명이 충분한지 또는 수치가 정확한지까지 보장하지 않는다.
- 근거 보충은 누락 대상을 드러내는 장치로, 모델 답변의 다른 오류를 수정하지 않는다.
- 재조사는 최대 1라운드, 작성은 기존 최대 3회. 데이터 수집 실패 시 부분 결과 반환은 아직 지원하지 않는다.
- 기본 v2에 적용하며 v1은 legacy다.
